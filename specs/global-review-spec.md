# 全局代码审核规范（兜底）

本文件在目标仓库**没有项目内规范**（AGENTS.md / CLAUDE.md / lint 配置等）时作为审核依据。目标仓库存在项目规范时，以项目规范为准，本文件不再适用。

## 1. 安全

- 用户输入进入 SQL / 命令 / 路径 / 正则时必须参数化或转义，禁止字符串拼接。
- 禁止硬编码凭证、密钥、内部地址；日志中不得输出敏感信息（token、密码、身份证号等）。
- 鉴权与越权：新增接口/数据访问必须有权限校验，注意水平越权（IDOR）。
- 反序列化、动态执行（eval/new Function/子进程拼接）需有白名单或充分理由。
- 依赖调用注意已知漏洞模式（如弱哈希、过时加密用法）。

## 2. Bug 与健壮性

- 边界条件：空集合、空字符串、0、负数、超长输入、并发重复提交。
- 错误处理：Promise/async 必须处理 rejection；catch 不得静默吞错；资源（文件句柄、连接、子进程）必须释放。
- 空值：外部输入（HTTP、文件、环境变量）默认不可信，先校验后使用。
- 并发：共享可变状态需说明保护机制；时序假设要显式。

## 3. 规范一致性（无项目规范时的通用底线）

- 命名：与所在文件/模块既有风格一致；布尔用 is/has/should 前缀，函数用动词开头。
- 单文件不过度膨胀（经验阈值 ~500 行），新函数职责单一。
- 导出的公共函数/类型需要注释说明用途、参数、失败行为。
- 禁止提交注释掉的死代码与调试残留（console.log / debugger）。

## 4. 性能

- 循环内避免重复的 IO/查询/大对象拷贝。
- 列表页禁止 N+1 查询模式。
- 明显的大数据全量加载（无分页/流式）需要指出。

## 5. 可维护性（只报显著问题）

- 同一逻辑出现第三处重复时指出应提取。
- 超长函数（>80 行）且包含多段不相干职责时指出。
- 魔法数字/字符串反复出现时应提为常量。

## 严重级别定义

| 级别 | 含义 |
|---|---|
| critical | 可被直接利用的安全漏洞，或必然发生的数据损坏/崩溃 |
| high | 高概率触发的 bug、明确的漏洞隐患、凭证泄漏 |
| medium | 特定条件下触发的 bug、显著性能问题、规范明显违反 |
| low | 可维护性建议、不确定性问题、风格改进 |
